# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project Overview

Sudoku and Cake for iOS: a fully offline, universal (iPhone + iPad) Sudoku app.
No accounts, no server, no sync, no tracking. The web app at
`../sudoku-and-cake` (Go + React) is the design and logic reference; this app is
a port of its engine, not a client for its API.

Plans live in `plans/`:
- `plans/sudoku-ios.md` — strategy and rationale
- `plans/implementation-plan.md` — the build sheet: file layout, type signatures,
  performance budgets, phased task breakdown with acceptance criteria

## Commands

All commands go through [Task](https://taskfile.dev).

| Command | What it does |
|---|---|
| `task install` | Resolve packages, report whether full Xcode is available |
| `task build:kit` | Build SudokuKit (no Xcode needed) |
| `task test:kit` | Run SudokuKit tests (no Xcode needed) |
| `task test:kit:cover` | Tests + coverage gate (SudokuKit must be ≥ 90%) |
| `task bench` | Generation performance harness (Gate G1) |
| `task lint` / `task format` | SwiftLint / swift-format |
| `task xcodegen` | Regenerate `SudokuApp.xcodeproj` from `project.yml` |
| `task test:app` | App tests on iPhone **and** iPad simulators (needs Xcode) |
| `task fixtures` | Regenerate the Go↔Swift cross-check fixture |

Single test: `swift test --filter RaterTests`

## Architecture

### Two build systems, deliberately

`SudokuKit/` is a plain SwiftPM package with no UIKit and no platform SDK, so
the entire game engine builds and tests with `swift test` on the command line.
Only the app shell needs Xcode. This is not incidental — it is what lets the
riskiest work (the technique rater) be developed and verified before any UI
exists.

`SudokuApp/` and `SudokuWidgets/` are generated by XcodeGen from
`SudokuApp/project.yml`. **The `.xcodeproj` is gitignored — never edit it, and
never commit it.** Change `project.yml` and run `task xcodegen`.

### SudokuKit

Pure logic, `Sendable` throughout, value types. Ported from the Go backend:

| Swift | Ported from |
|---|---|
| `Techniques.swift`, `Rater.swift` | `backend/internal/generator/difficulty.go` |
| `Solver.swift`, `Generator.swift` | `backend/internal/generator/generator.go` |
| `Validator.swift` | `backend/internal/validator/validator.go` |
| `Achievements.swift` | `backend/internal/achievements/achievements.go` |
| `Streak.swift`, `StatsAggregator.swift` | `backend/internal/store/store.go` |
| `HintEngine.swift`, `ShareCode.swift`, `DailyPuzzle.swift` | new — no web equivalent |

### Rules that are load-bearing

1. **Never call the global RNG in SudokuKit.** Dailies must be reproducible on
   every device forever. Thread `inout SeededRandom` through every draw, and use
   `deterministicShuffle(using:)` rather than `Array.shuffle` — the stdlib's
   algorithm is not a stable contract. SwiftLint enforces this; the custom rules
   are errors, not warnings.

2. **Do not "improve" the rater's loop order.** `Rater.rate` applies techniques
   cheapest-first and returns the hardest tier reached. The order *is* the
   difficulty definition. Changing it re-rates every puzzle.

3. **The cross-check fixture is the proof the port is correct.**
   `Tests/SudokuKitTests/Fixtures/tier-corpus.json` holds puzzles rated by the Go
   implementation. If a rater change makes it fail, the change is wrong until
   proven otherwise — do not regenerate the fixture to make tests pass.

4. **No allocation in the carve loop.** Hot paths take `borrowing Grid` and use
   `withUnsafeTemporaryAllocation` for scratch. Go's fixed-size arrays copy for
   free; Swift's do not. This is the difference between a fast generator and a
   spinner on "New game".

5. **SwiftData models stay CloudKit-shaped** even though sync is off: no
   `@Attribute(.unique)`, every property optional or defaulted, and no
   relationships at all — rows reference each other by `UUID`. Sync should later
   be one line, not a migration. **The schema is frozen**: see
   `plans/schema-v1.md`. Later phases add entities and optional fields; they do
   not rename, retype or re-encode anything.

6. **Nothing outside `Persistence/` touches a `ModelContext` or a `@Model`
   class.** Views and tests go through `GameRepository`, which trades in value
   types. That is what lets the whole persistence layer be swapped for an
   in-memory implementation in tests, and what keeps non-`Sendable` model objects
   out of the view layer.

7. **No OCR / photo import.** Tried twice in the web app and removed; manual
   entry replaced it. Do not reintroduce it.

## Testing

Swift Testing (not XCTest) for SudokuKit. Go test tables are ported directly.
Beyond examples, the suite asserts properties: every generated puzzle has exactly
one solution, rates inside its difficulty band, and never requires guessing.

Coverage floor for SudokuKit is 90% and enforced in CI.

## Code Style

SwiftLint (`--strict`) and swift-format, both configured at the repo root.
Short identifiers (`r`, `c`, `n`, `k`, `br`, `bc`) are allowed on purpose: they
match the Go source, which keeps the port reviewable line by line.
